# PRS Airdrop Bot + Web Portal

پنل وب مستقل برای ربات فعلی PRS؛ با ورود از ربات، حساب مشترک و مدیریت مأموریت‌ها.

**این نسخه یک Telegram Mini App نیست. توکن PRS روی BNB حفظ می‌شود. پنل هیچ توکن جدیدی ایجاد و هیچ تراکنش بلاکچینی ارسال نمی‌کند.**

## امکانات

- رابط واکنش‌گرا و دوزبانه فارسی/انگلیسی، شامل نمای کلی، مأموریت‌ها، دعوت‌ها، رتبه‌بندی و حساب.
- لینک ورود شخصیِ ۵ دقیقه‌ای و یک‌بارمصرف؛ نشست سمت سرور با کوکی امن و محافظت CSRF.
- مأموریت سؤال با بررسی خودکار و مأموریت مدرک متنی/لینک با بررسی مدیر؛ یک‌باره، روزانه یا هفتگی.
- بودجه، ظرفیت، مهلت، دفعات تلاش و رزرو پاداش برای مدارک در انتظار بررسی.
- دریافت مشترک پاداش روزانه از سایت یا ربات؛ جلوگیری از دریافت دوباره در بازه ۲۴ساعته.
- نمایش موجودی پاداش ثبت‌شده، پرداخت‌ها، سابقه فعالیت و پیگیری درخواست پرداخت.
- مدیریت مأموریت، تأیید/رد مدرک، ثبت تراکنش پرداخت‌شده و پاسخ پشتیبانی.
- اجرای مأموریت‌های جدید در ربات معمولی، بدون اجبار کاربر به ورود به سایت.
- حالت آزمایشی با حساب‌ها و اطلاعات کاملاً ساختگی و بدون اتصال به Telegram یا MongoDB واقعی.

## حفظ قواعد فعلی ربات

مقادیر فعلی در `portal/settings.py` متمرکز شده‌اند و بدون تغییر باقی می‌مانند:

| قاعده | مقدار |
| --- | --- |
| حدنصاب دعوت | ۳ |
| پاداش پایه پس از حدنصاب | ۲٬۰۰۰ PRS |
| هر دعوت اضافه پس از حدنصاب | ۵٬۰۰۰ PRS |
| پاداش روزانه | ۱٬۰۰۰ PRS / هر ۲۴ ساعت |
| سقف موجود کمپین | ۳۰۰٬۰۰۰٬۰۰۰ PRS |
| ثبت کیف پول | پس از حدنصاب دعوت؛ یک‌بار ثبت و یک‌بار اصلاح |

چالش قدیمی، ثبت شبکه‌های اجتماعی، گزارش‌ها و امکانات مدیریتی قبلی ربات حفظ شده‌اند. مأموریت‌های جدید یک بخش جدا هستند. پاداش مأموریت‌های جدید در `manual_bonus_tokens` ثبت می‌شود تا مجموع‌ها و گزارش‌های قبلی ربات آن‌ها را هم لحاظ کنند. تاریخچه اختصاصی مأموریت‌ها در `portal_history` قرار دارد.

## نصب و آزمایش

Python 3.12 استفاده شده است.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
pytest -q
node --check static/app.js
```

برای حالت آزمایشی، در یک محیط فاقد `BOT_TOKEN` و `MONGO_URL` اجرا کنید:

```bash
PORTAL_DEMO=1 python web.py
```

آدرس محلی: `http://127.0.0.1:8000`. صفحه ورود دو گزینه «حساب نمونه» و «مدیریت نمونه» دارد. اطلاعات آزمایشی حافظه‌ای‌اند و با راه‌اندازی مجدد پاک می‌شوند. این حالت فقط برای بررسی است و نباید کنار اعتبارنامه‌های واقعی فعال شود.

## اجرای واقعی

راهنمای فارسی مرحله‌به‌مرحله در [DEPLOY_RAILWAY_FA.md](DEPLOY_RAILWAY_FA.md) است.

دو سرویس مستقل از همین مخزن:

| سرویس | دستور اجرا |
| --- | --- |
| ربات؛ فقط یک نمونه | `python bot.py` |
| وب | `gunicorn 'web:create_app()' --bind 0.0.0.0:$PORT --workers 2 --timeout 45 --access-logfile -` |

متغیرهای لازم در `.env.example` فهرست شده‌اند. **مقادیر واقعی را در Railway Variables وارد کنید، نه در GitHub.**

`PORTAL_ENABLED` پیش‌فرض خاموش است. تا آماده‌شدن وب و موفقیت بررسی MongoDB، آن را روشن نکنید. در حالت خاموش، ربات بدون اضافه‌کردن منوهای وب به کار خود ادامه می‌دهد؛ دریافت روزانه قدیمی نیز با شرط اتمیک زمان، روی MongoDB مستقل قابل اجراست.

## پیش‌نیاز مهم MongoDB

نسخه واقعی پنل به MongoDB replica set یا sharded cluster با پشتیبانی transaction نیاز دارد؛ MongoDB Atlas معمولاً این قابلیت را دارد، اما اتصال فعلی باید بررسی شود. MongoDB مستقل (standalone) برای این نسخه کافی نیست. در این حالت پنل به روش ناامن جایگزین برنمی‌گردد.

پیش از فعال‌سازی:

```bash
python scripts/prepare_portal.py
```

این دستور قابلیت transaction، تکراری‌نبودن شناسه کاربران و ایندکس‌های مجموعه‌های جدید را بررسی می‌کند؛ اطلاعات کاربران و موجودی‌ها را حذف یا بازنویسی نمی‌کند. در `/readyz` نیز قابلیت transaction بررسی می‌شود.

## محدوده و نکات عملیاتی

- ارسال عکس/فایل مدرک در نسخه اول پیاده نشده؛ مدرک به‌شکل متن یا لینک ثبت می‌شود.
- ثبت پرداخت توسط مدیر، اثبات خودکار تراکنش روی BNB نیست. مدیر باید مبلغ، شبکه، آدرس و موفقیت تراکنش را در خارج از پنل بررسی کند؛ سپس هش را ثبت کند. هش تکراری و ثبت دوباره همان درخواست رد می‌شود.
- برای جلوگیری از تعارض، درخواست‌های پرداخت پنل را از خود پنل بررسی کنید. اگر قبلاً با ربات پرداختی ثبت شده باشد، پنل تغییر مانده را تشخیص داده و از ثبت مبلغ بیش از مانده جلوگیری می‌کند.
- کنترل بودجه مأموریت و دریافت‌های جدید در transaction انجام می‌شود. مسیرهای قدیمی دعوت، پاداش همگانی و پاداش دستی همان منطق قبلی خود را دارند؛ سقف کلی ایردراپ در رقابت با عملیات قدیمی تضمین سراسری جدیدی ندارد. هم‌زمان با پاداش‌های انبوه قدیمی، کمپین‌های جدید را متوقف کنید یا مرحله بعدی یکپارچه‌سازی کامل دفتر پاداش را انجام دهید.
- پاداش ثبت‌شده حساب، موجودی کیف پول روی بلاکچین نیست و تبدیل قیمت/نقدشوندگی را تضمین نمی‌کند.
- لینک ورود حاوی کلید یک‌بارمصرف در fragment است؛ کلید خام در دیتابیس یا URL درخواست سرور ذخیره نمی‌شود. دریافت کلید از لینک و تبدیل آن به نشست، فقط با JavaScript همین دامنه انجام می‌شود.
- `PORTAL_DEMO=1` در صورت وجود اعتبارنامه واقعی از اجرا جلوگیری می‌کند؛ ورود مدیریت نمونه در حالت واقعی در دسترس نیست.
- بررسی عضویت کانال به ادمین‌بودن ربات در کانال نیاز دارد. هنگام خطای API تلگرام، پاداش جدید ثبت نمی‌شود.
- وب و ربات باید به **همان دیتابیس و همان مجموعه users** متصل باشند؛ وب نباید `bot.py` را اجرا کند.
- تست‌ها از حافظه ایزوله استفاده می‌کنند. اجرای زنده Telegram، MongoDB واقعی، DNS و Railway باید پس از اتصال حساب‌ها بررسی شود. بررسی بصری مرورگر در محیط ساخت در دسترس نبود.
- این پنل هنوز روی Railway منتشر نشده و شاخه اصلی مخزن در این بسته به‌صورت خودکار تغییر نمی‌کند.

## ساختار

```text
bot.py                       ربات موجود + اتصال اختیاری پنل
web.py                       وب مستقل با Flask
portal/settings.py           تنظیمات مشترک
portal/service.py            قواعد ورود، مأموریت، پاداش و پرداخت
portal/store.py              MongoDB و حافظه آزمایشی
portal/bot_bridge.py          مأموریت و ورود پنل در ربات معمولی
portal/demo.py                داده‌های ساختگی
templates/index.html          قالب اصلی
static/app.css, app.js        رابط کاربری
scripts/prepare_portal.py      بررسی غیرمخرب پیش از فعال‌سازی
tests/                        آزمایش‌های عملکرد و امنیت
```
